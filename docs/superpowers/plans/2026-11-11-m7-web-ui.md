# M7. Веб-интерфейс — план реализации

> **Для исполнителя:** скилл `superpowers:executing-plans`, тест раньше кода.
> План содержит задачи, интерфейсы, тесты и команды проверки, без кода реализации.

**Цель:** страница в браузере: текстовый запрос → 2–3 маршрута на карте со статистикой, профилем
высот и GPX; уточнение следующей репликой; ответы на вопросы сервиса кнопкой или кликом по
карте; места, сохранённые маршруты, слой личной теплокарты.

**Архитектура:** одностраничное приложение в `web/` (Vite + TypeScript + React + MapLibre GL JS,
тайлы OpenFreeMap), без роутера и стейт-библиотек. Вся логика диалога — чистые функции
(`session.ts`, `chips.ts`, `geo.ts`), покрытые vitest; компоненты только рисуют. Собранный
`web/dist` раздаёт тот же FastAPI, что и API. Серверу добавляются три вещи: геометрия проеханных
дорог, сохранённые маршруты, раздача статики.

**Стек:** Node 24 LTS, Vite, React, TypeScript (strict), maplibre-gl, vitest. Зависимости ставятся
с `npm install --before=<дата двухнедельной давности>`.

## Общие ограничения

- Тексты интерфейса — на русском; код и комментарии — на английском.
- Браузер ходит только к своему серверу и за тайлами карты (OpenFreeMap). Треки и теплокарта
  наружу не уходят.
- В тестах и примерах только публичные и синтетические координаты.
- `pytest` не требует Node; фронтенд проверяется отдельно: `npm test`, `npm run build`.
- `web/dist` и `node_modules` в git не попадают.

## Протокол диалога (как интерфейс ходит в API)

- Реплика → `POST /api/parse {text, click?, request_id?}`. `request_id` — номер текущего
  результата: пока он есть, каждая реплика считается уточнением.
- `click` отправляется, только если пользователь передвинул маркер старта после последнего
  результата; после результата маркер встаёт на `spec.start` и «свежим» не считается.
- Ответ с `question`: варианты — кнопками и маркерами на карте; выбор → повтор с `understood` и
  `picks[about]`. Клик по карте при вопросе: `about = "start"` → `click`; иначе `picks[about]`
  (подпись — само название). Ответ словами: на вопрос о длине число подставляется в
  `understood.length_km` без модели; иначе новый вызов с текстом «исходная реплика. ответ».
- Ответ со `spec` → `POST /api/route`. Правка чипов → `POST /api/parse` с изменённым
  `understood` в обстановке исходной реплики: те же `picks`, `request_id` и `click` (старт и
  «как вариант 2» сохраняют смысл).
- Чипы не показывают значения по умолчанию (`avoid_major 0.5`, `familiarity 0.4`, `forest 0.3`,
  `surface any`, `hills any`): после уточнения модель возвращает их явно.

### Задача 1. Сервер: теплокарта, сохранённые маршруты, статика

**Интерфейс:**
- `GET /api/heatmap` → GeoJSON `FeatureCollection` с `bbox` проеханных дорог; по одному
  `MultiLineString` на уровень, `properties: {level: 0…4, label: "1" | "2–4" | "5–14" | "15–49" | "50+"}`;
  координаты до 5 знаков; собирается один раз, отдаётся сжатым (`GZipMiddleware`); без истории
  заездов — 404.
- `POST /api/routes {candidate_id, name?}` → 201 `{id, name, created, length_km, ascent_m}`
  (имя по умолчанию — заголовок кандидата; неизвестный кандидат — 404);
  `GET /api/routes` (новые сверху); `GET /api/routes/{id}` → то же плюс `spec` и `candidate`;
  `GET /api/routes/{id}.gpx`; `DELETE /api/routes/{id}` → 204. Сохранённый маршрут не зависит от
  очистки последних запросов.
- `create_app(..., static_dir=None)`: каталог с `index.html` раздаётся с корня; `/api/*` важнее.
  `config.web_dist()` — `RPA_WEB_DIR` либо `web/dist` рядом с пакетом.

**Тесты:** `tests/test_db.py` — сохранение копирует кандидата и его запрос, переживает вытеснение
запроса, список в обратном порядке, удаление; `tests/test_api.py` — круг жизни сохранённого
маршрута и его GPX, 404-е; теплокарта на сетке с заездами (уровни, bbox, сжатие) и 404 без них;
статика: `/` отдаёт `index.html`, `/api/meta` работает, без каталога `/` — 404;
`tests/test_cli.py` — `serve` передаёт каталог интерфейса.

### Задача 2. Каркас фронтенда и логика

`web/`: `package.json` (скрипты `dev`, `build`, `test`), `vite.config.ts` (прокси `/api` на
`127.0.0.1:8000`), строгий `tsconfig`.

**Интерфейс:**
- `api.ts`: типы `Point`, `RouteSpec`, `ParsedRequest`, `Question`, `Candidate`, `RouteResponse`,
  `ParseBody`, `ParseResponse`, `Place`, `SavedRoute`, `Meta`; функции по одной на эндпоинт;
  `ApiError` с русским текстом из `detail`.
- `session.ts`: `Pending` (реплика, ждущая ответа); `answerWithOption`, `answerWithPoint`,
  `answerWithText`, `lengthFromAnswer`, `refinement` — каждая возвращает тело для `/api/parse`.
- `chips.ts`: `chips(understood, spec) -> Chip[]`, `without(understood, chip) -> ParsedRequest`.
- `geo.ts`: `along(line) -> number[]` (накопленные метры), `pointAt(line, along, metres)`,
  `bounds(lines)`.

**Тесты (vitest):** каждый пункт «Протокола диалога» — отдельный тест `session.test.ts`;
чипы: значения по умолчанию скрыты, удаление чипа обнуляет своё поле и только его, диапазон длины
одним чипом; геометрия: длина известного отрезка, точка на середине, границы.

### Задача 3. Компоненты

- `MapView`: карта, маркер старта (клик двигает), линии кандидатов (выбранный поверх и толще;
  клик выбирает), маркеры вариантов ответа, точка под курсором профиля, слой теплокарты с
  легендой, атрибуция OSM / Copernicus / ESA WorldCover.
- `Chat`: лента реплик, вопрос с кнопками-вариантами, поле ввода, «Новый маршрут».
- `Chips` + `RequestEditor`: как понят запрос; крестик снимает условие; редактор — длина,
  покрытие, холмы, три ползунка.
- `CandidateCard`: длина, набор, доли леса / знакомых / крупных / грунта, пометка, GPX, «Сохранить».
- `ElevationProfile`: SVG, подписи высот и расстояния, наведение двигает точку на карте.
- `PlacesPanel`, `SavedRoutesPanel`.
- Вёрстка: панель слева, карта справа; на узком экране панель снизу.

**Проверка:** `npm run build` без ошибок типов; `npm test`.

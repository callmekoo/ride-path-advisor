# M10. Несколько точек и маршруты без длины — план реализации

> **Для исполнителя:** скилл `superpowers:subagent-driven-development`, тест раньше кода.
> План содержит задачи, интерфейсы, тесты и команды проверки, без кода реализации.
> Дизайн: `docs/superpowers/specs/2026-11-15-walk-via-around-design.md`. Ветка `m10-via-list`.

**Цель:** маршрут задаётся любым числом точек — словами («из A в B через C и D») и кликами по
карте; линию маршрута можно потянуть и поставить промежуточную точку; длину можно не называть.

**Архитектура:** `RouteSpec.via` становится упорядоченным списком. Генератор ведёт цепочку
`старт → точки → финиш` существующим `walk.route_through` и разнообразит её повторными проходами
со штрафом за уже использованные дороги. Точки с карты приходят в `/api/parse` списком, роли
раздаёт чистая функция в `nlu/resolve.py`. Кольцо без длины и без мест — три размера из истории
заездов.

**Стек:** без новых зависимостей. Python (pydantic, numpy), TypeScript (React, MapLibre).

## Общие ограничения

- Совместимость со старым форматом `RouteSpec` не нужна: история запросов и сохранённые
  маршруты в `rpa.sqlite` очищаются при смене версии схемы; **сохранённые места остаются**.
- Порядок точек — как назвал или накликал пользователь; сервис его не переставляет.
- В модель уходят только текст запроса, названия мест и статистика вариантов; координаты — нет.
- Схема `ParsedRequest` остаётся плоской (`tests/test_prompt.py` запрещает `$defs`).
- Инвариант ядра: вес дуги равен `+inf` либо не меньше длины ребра.
- В тестах и эталонных запросах — только публичные точки.
- Не проверять на настоящем `data/` загрузку треков и `sync-tracks`; `rpa match` и
  `rpa build-graph` на настоящих данных — можно.
- Код, комментарии, коммиты — на английском; строки для пользователя — на русском. Коммит
  заканчивается строкой `Co-Authored-By`, как в истории.
- После правки промпта `rpa nlu-eval` запускает пользователь (тратит токены).

## Модели для задач

Простые и хорошо описанные задачи — Sonnet; генератор (задачи 2 и 3) — самая сильная доступная
модель; итоговая проверка ветки — сильная модель; правки в одну строку — Haiku. Работа с
настоящим `data/` и браузером — основная сессия.

### Задача 2. Генератор: цепочка точек — *сильная модель*

**Интерфейс (`routing/walk.py`, `routing/generate.py`):**
- `Walk = tuple[np.ndarray, tuple[int, ...]]` — дуги и узлы, которые маршрут обязан содержать,
  по порядку (вместо одного `via`). Для воды — один узел, как сейчас.
- `walk.route_legs(engine, w, nodes, may_turn_back_at) -> list[np.ndarray] | None` — плечи по
  отдельности; `route_through` становится их склейкой, поведение не меняется.
- `_walk_via_places(engine, w, nodes, places: frozenset[int])` вместо `_walk_via_place`:
  сначала без разворотов, затем с разворотом в любой из точек; обрезка хвостов (`trim_spurs`)
  по каждому отрезку между соседними точками, границы — по плечам, а не поиском узла.
- `_passes_in_order(engine, arcs, required) -> bool`: проход по `[хвост первой дуги, *головы дуг]`
  с проверкой порядка; заменяет `via in engine.arc_head[arcs]` и покрывает точку, совпавшую
  со стартом.
- `generate`: `places = [_place_node(...) for p in spec.via]`, подряд идущие дубликаты и точки,
  совпавшие с соседним стартом или финишем, выбрасываются.
- `_through_places(engine, w, start, places, end, spec)` вместо `_through_place`.
- `_chain_alternatives(engine, w, nodes, places, count)`: приём `_alternatives` на всей
  цепочке — после каждого прохода рёбра маршрута дорожают в `ALTERNATIVE_FACTOR` раз, цепочка
  прокладывается заново; оценка — по исходным весам.
- `_detours(..., lead: list[int])` вместо `before`: удлиняется только последнее плечо.
- Если после отбора вариантов меньше `n_candidates` — добор с `VIA_MAX_OVERLAP = 0.6`.
- `Candidate.via_label` — строка: подписи точек через « → ».

**Длина вместе с точками:**

| Случай | Результат |
|---|---|
| длины нет | прямая цепочка, её альтернативы и объезды `PLACE_DETOUR` |
| `max` меньше прямой цепочки | прямая и альтернативы с пометкой «через A, B короче N км не получится» |
| прямая в допуске | прямая и альтернативы |
| прямая короче `min` | `_detours(lead=…)` |

`bearing_deg` при точках игнорируется, как сейчас; `avoid` действует через веса.

**Тесты (`test_walk.py`, `test_generate.py`, сетка 21×21):** две точки по порядку; обратный
порядок даёт другой маршрут; кольцо через два места без длины; удлинение до заданной длины;
пометка, когда короче нельзя; подпись через « → »; точка, совпавшая со стартом; далёкая точка
даёт не меньше двух вариантов; точка в тупике проходится с разворотом.

**Проверка:** `uv run pytest -q tests/test_walk.py tests/test_generate.py`, затем `uv run pytest -q`.

### Задача 3. Кольцо без длины: три размера — *сильная модель* (генератор), *Sonnet* (размеры из истории)

**Интерфейс:**
- `Engine.loop_sizes_km: tuple[float, float, float]`, по умолчанию
  `DEFAULT_LOOP_SIZES_KM = (30.0, 50.0, 80.0)`; `Engine.set_loop_sizes(sizes | None)`.
- `_loops(..., length: LengthKm | None, ...)`: при `None` достижимость и «приятные» узлы
  считаются один раз, попытки — по 6 азимутов на размер со сдвигом 0° / 10° / 20° (54 вместо 36).
- Каждая группа измеряется, отбраковывается и оценивается против `LengthKm.around(size, 0.15)`;
  для этого цикл кандидатов из `generate` выносится в `_candidates(engine, w, walks, spec, note)`.
- `diversity.select_by_size(groups, edge_len, max_overlap) -> list[Candidate]`: на размер —
  лучший кандидат с перекрытием ≤ 0,4 с уже выбранными, иначе лучший в группе. Порядок — от
  короткого к длинному. `note` остаётся `None`.
- `rpa.match.sizes.ride_sizes_km(tracks: TrackSet) -> tuple[float, float, float] | None`:
  квартили 25 / 50 / 75 длины заездов (сумма сегментов трека; без `commute` и короче 10 км),
  округление до 5 км, соседние размеры различаются не меньше чем на 20 %, иначе `None`;
  меньше 20 заездов — `None`.
- `rpa match` пишет `ride_sizes.json` рядом с `rides.npy` (`{"km": [a, b, c]}`); `build-graph`
  переносит файл из прежнего каталога графа, если он есть; `load_engine` читает его;
  `api/app.py::_RidesFile` перечитывает вместе с `rides.npy`.
- `nlu/resolve.py`: вопрос «На сколько километров кольцо?» удаляется.

**Тесты:** `test_generate.py` — при `engine.set_loop_sizes((6, 10, 16))` три варианта с длинами
по возрастанию, каждый в ±15 % своего размера; с водой (`via_category`) — то же; `test_score.py`
— `select_by_size`; новый `test_sizes.py` — квартили, исключение `commute` и коротких, мало
заездов, слипшиеся размеры; `test_engine.py`, `test_cli.py`, `test_api.py` — файл читается,
подменяется без перезапуска; `test_resolve.py` — кольцо без длины даёт спек, а не вопрос.

**Проверка:** `uv run pytest -q`.

### Задача 5. Разбор текста: список мест и роли точек — *Sonnet*; формулировки промпта — основная сессия

**Интерфейс:**
- `ParsedRequest.via: list[str] = []`. `SYSTEM`: «через C и D» — список в порядке упоминания;
  «до X и обратно» — кольцо с `via = ["X"]`. `describe()` отдаёт подписи всех точек.
- `Context.points: list[Point]` вместо `click`.
- Чистая функция `assign_points(points, start_named, end_named, loop) -> tuple[Point | None, list[Point], Point | None]`
  (старт, промежуточные, финиш):
  - ничего не названо: первая — старт, последняя — финиш, остальные — промежуточные; одна
    точка — только старт;
  - назван старт: все точки промежуточные, последняя — финиш;
  - назван финиш или `loop`: последняя точка тоже промежуточная;
  - `loop` и ничего не названо: первая — старт, остальные — промежуточные.
- Названные словами промежуточные места идут раньше кликнутых. Кликнутые точки получают метки
  «точка 1», «точка 2»… по порядку в списке.
- Форма: `parsed.shape`, иначе `p2p`, если есть финиш (названный или последняя точка), иначе
  `loop`.
- Порядок выбора старта прежний: названное место → первая кликнутая точка → прежний старт →
  место по умолчанию → вопрос.
- `nlu/cases.py`: формулировки с двумя и тремя местами, кольцо без длины, «по лесу от дома»
  без длины; `evaluate._matches` сравнивает списки мест по порядку.

**Тесты:** `test_resolve.py` — все ветви `assign_points`, смешение названных и кликнутых,
тёзка в середине списка даёт вопрос с `about` = название; `test_prompt.py` — каждое поле
объяснено, схема плоская; `test_nlu_evaluate.py` — сравнение списков.

**Проверка:** `uv run pytest -q`. Живая модель: `uv run rpa nlu-eval` — пользователь.

### Задача 7. Страница: точки кликами — *Sonnet*

**Поведение:**
- Клик по карте добавляет точку в конец списка. При двух и более точках маршрут строится
  сразу, без текста (пустой `text`, `understood` из прошлого ответа либо пустой).
- При ожидании ответа на вопрос и на вкладке «Места» клик работает как сейчас.
- Маркеры нумерованные: старт, промежуточные 1…n, финиш; перетаскиваются
  (`Marker({draggable: true})`), отпускание пересобирает запрос. Клик по маркеру убирает точку;
  клик по маркеру **старта** при двух и более точках замыкает маршрут в кольцо
  (`understood.shape = "loop"`), повторный — размыкает.
- Чипы: по чипу на каждую промежуточную точку («через: точка 1 ✕», «через: Дегтярск ✕»);
  крестик убирает кликнутую точку из списка либо название из `understood.via`.
- Любая правка точек пересобирает запрос через `understood`, без вызова модели.
- «Старт отсюда» на вкладке «Места» ставит первую точку.

**Интерфейс (`session.ts`, чистые функции с тестами):** `Turn.points: Point[]` вместо `click`;
`withPoint(turn, point)`, `withoutPoint(turn, index)`, `movedPoint(turn, index, point)`,
`closedLoop(turn, closed)`; тело запроса — `points`. Ветка ответа на вопрос о длине удаляется.
`Chat.tsx`: в примерах появляется запрос без длины и запрос «через … и …».

**Тесты:** `session.test.ts`, `chips.test.ts`.

**Проверка:** `cd web && npm test && npm run build`; руками или в headless Chromium — два клика
дают маршрут, третий делает прежний финиш промежуточной точкой, перетаскивание и удаление
маркера, замыкание кольца.

### Задача 8. Страница: перетаскивание линии маршрута — *Sonnet*, проверка в браузере — основная сессия

**Поведение:** нажатие на линию выбранного маршрута и движение создаёт временный маркер; при
отпускании он становится промежуточной точкой и запрос пересобирается. Нажатие без движения
(меньше 5 px) по-прежнему выбирает вариант. На сенсорном экране захват — долгим нажатием
(350 мс), чтобы не мешать прокрутке карты. Пока тянут, карта не двигается
(`map.dragPan.disable()`), маршрут не пересчитывается.

**Интерфейс (`geo.ts`):** `insertIndex(line: LonLat[], points: LonLat[], grabbed: LonLat) -> number`
— место новой точки в списке: для каждой точки и для места захвата берётся индекс ближайшей
координаты линии; новая точка встаёт перед первой точкой, чей индекс больше. Точки — те, что
лежат на маршруте в порядке прохождения (старт, промежуточные, финиш); если старт назван
словами и в списке кликов его нет, индексы считаются от промежуточных.

**Тесты (`geo.test.ts`):** захват между стартом и первой точкой; между двумя промежуточными;
перед финишем; кольцо (старт в начале и в конце линии); маршрут без промежуточных точек.

**Проверка:** `cd web && npm test && npm run build`; в браузере — тянуть линию в трёх местах,
точка встаёт между правильными соседями; на узком экране — долгим нажатием.

### Задача 9. Эталоны, реальные данные, документы — основная сессия

- `eval/run.py::check`: точки пройдены по порядку (первая координата в пределах
  `VIA_REACH_M = 500` от каждой точки, индексы не убывают); для кольца без длины — три длины,
  соседние различаются не меньше чем на 20 %.
- `eval/cases.py`: `p2p-revda-via-degtyarsk` (Екатеринбург → Ревда через Дегтярск),
  `loop-via-two` (кольцо из Екатеринбурга через Верхнюю Пышму и Берёзовский без длины),
  `loop-no-length` (кольцо без длины; размеры по умолчанию задаются в самом эталоне, чтобы не
  зависеть от истории). Координаты — из указателя названий, не по памяти.
- `uv run rpa match` (пишет `ride_sizes.json`), `uv run rpa eval` — код 0, каждый запрос ≤ 5 с;
  замер времени кольца без длины.
- `curl --noproxy '*'`: `/api/parse` → `/api/route` для «из A в B через C и D», «кольцо через
  Ревду и Дегтярск», «кольцо по лесу от дома»; сервер стартует на прежней базе и не падает.
- Браузер: сценарии задач 7 и 8.

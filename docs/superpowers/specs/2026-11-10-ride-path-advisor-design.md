# ride-path-advisor — дизайн и план реализации

> Исходный дизайн от 2026-11-10, до начала реализации. Текущее состояние, оставшиеся этапы и
> отличия кода от этого документа — в [`docs/roadmap.md`](../../roadmap.md); при расхождении прав roadmap.

## Контекст

Есть архив ~5000 велотреков (мои и друга, в Strava). Хочется по текстовому запросу
(«заезд около 45 км к воде, желательно по лесу, меньше больших дорог»; «80 км от Дидинского
тоннеля до Екатеринбурга, поменьше дорог»; «шоссейный заезд на 100–150 км, кольцевой»)
получать 2–3 заметно разных маршрута на карте со статистикой и GPX, а потом уточнять их текстом
(«короче», «не через Ревду»). Маршрут строится по дорожному графу OSM; уже проеханные дороги
получают бонус, непроеханные остаются допустимыми.

Проект с нуля. Дизайн прошёл три исследования (роутинг-движки, Strava/данные, алгоритмы колец) и критическое
ревью субагента-архитектора; его правки уже внесены ниже.

## Принятые решения

| Вопрос | Решение |
|---|---|
| Масштаб | Личный инструмент на двоих, **без логинов**, общая база треков и общий список мест. Слушает localhost/LAN; наружу — только за VPN/reverse-proxy |
| Регион | Свердловская область **+ буфер ~100 км**: пообластные выгрузки download.openstreetmap.fr (Свердловская + соседи) → `osmium merge` → `osmium extract` по полигону области с буфером. Список выгрузок и буфер — в конфиге. Один и тот же итоговый pbf (sha256 в метаданных) идёт и в свой граф, и в тайлы Valhalla |
| Треки | ZIP «Скачать свои данные» Strava (activities.csv + GPX/FIT/TCX) + папка/загрузка новых файлов. Strava API не используем (политика с июня 2026: хранение ≤7 дней, запрет агрегации, платный доступ). Берём только велозаезды, без виртуальных |
| Роль треков | Предпочтение: бонус проеханным рёбрам, сила «прилипания» — параметр запроса `familiarity` |
| Профили | Один общий; «шоссейный» = режим покрытия `paved` по данным OSM |
| Разбор текста | Облачная LLM через тонкий OpenAI-совместимый слой: `LLM_BASE_URL`, `LLM_MODEL`, `LLM_API_KEY`, **`LLM_PROXY_URL`** (http/https/socks5; `httpx[socks]`, `trust_env=False` — прокси только для LLM-вызовов). Данные треков в LLM не уходят |
| Результат | 2–3 варианта + статистика + профиль высот + GPX; уточнение текстом поверх предыдущего запроса |
| Старт | Сохранённые места («дом» по умолчанию) → клик по карте → иначе сервис задаёт уточняющий вопрос |
| Ядро | Свой граф из OSM + маленькое Rust-ядро поиска пути (PyO3/maturin, abi3); вся эвристика на Python. Привязка треков — Valhalla (pyvalhalla) отдельным пакетным процессом |
| Хостинг | Не выбран → один образ (podman/docker-совместимый) и для сервера, и для пакетных команд |

## Архитектура

```
 пообластные pbf ─► merge+clip ─► region.pbf ─┬─► osm/build ─► graph/<sha>-<ver>/ (npy-массивы)
                                              ├─► gazetteer.sqlite (топонимы, FTS5)
                                              └─► тайлы Valhalla ─┐ (только пакетно)
 Strava ZIP / папка ─► tracks/ingest ─► clean ─► match ─► сегменты (way_id + концы) ─► project ─► rides[edge]
 Copernicus GLO-30, ESA WorldCover, OSM water ─► enrich ─► ascent, forest, water_nodes, профили высот

 текст ─► /api/parse: один вызов LLM (структурированный вывод) ─► сервер резолвит топонимы (FTS)
        ─► RouteSpec | уточняющий вопрос
 RouteSpec ─► /api/route: cost (prefs → веса дуг, numpy) ─► generate ⇄ kernel (Rust: A*, SSSP)
        ─► trim ─► score ─► diversity ─► 2–3 кандидата (GeoJSON, статистика, GPX)
 web (React + MapLibre, тайлы OpenFreeMap) ⇄ FastAPI ⇄ SQLite (места, сессии, маршруты)
```

Центральный контракт — `RouteSpec` (pydantic): `start`, `end|None`, `shape: loop|p2p`,
`length_km {target,min,max}` («около 45» → ±10%; «100–150» → жёсткий диапазон),
`via [place | category: water|…]`, `prefs {forest, avoid_major, familiarity, surface: any|paved|prefer_unpaved, hills}`,
`avoid [{place, radius_m}]`, `anchor_candidate?`, `n_candidates`.
LLM и UI производят RouteSpec, движок потребляет только его.

## Компоненты

Корень — uv-workspace: Python-пакет `src/rpa/` (Python 3.14), Rust-крейт `kernel/` (maturin), фронтенд `web/`.

1. **`osm/`** — `tags.py`: чистая табличная функция `classify_way(tags) -> EdgeAttrs | None`
   (класс дороги; покрытие 6 классов `paved / likely_paved / unknown / likely_unpaved / unpaved / bad`
   с выводом `surface` → `tracktype` → класс дороги, т.к. `surface` заполнен лишь у ~20–30% сельских
   дорог; доступ и односторонность по направлениям; флаг «мягкое ограничение» для
   `access=private|destination` и footway). Жёстко выбрасываются при сборке: motorway, motorroad,
   `winter_road`/`ice_road` (в регионе их тысячи), construction, steps.
   `build.py`: проход pyosmium → рёбра = куски одного OSM-пути между узлами разреза (общий для ≥2
   путей, конец пути, барьер); **степень-2 не схлопываем** — атрибуты однородны на ребре.
   Только главная компонента связности. `gazetteer.py`: все именованные объекты, включая
   непроезжие (тоннели, станции, вершины, водоёмы), в SQLite FTS5; при использовании —
   привязка к ближайшему проезжему узлу с предупреждением, если дальше 500 м.
2. **`graph/`** — `store.py` (каталог `.npy` + `meta.json`, mmap), `snap.py` (cKDTree).
   Формат: `node_lonlat f64[N,2]`, `edge_u/edge_v u32[E]`, `edge_len_m f32[E]`, `edge_way_id i64[E]`,
   `edge_way_pos u16[E,2]`, `edge_highway/edge_surface u8[E]`, `edge_flags u16[E]`,
   геометрия `geom_off u32[E+1]` + `geom_xy i32[P,2]` (×1e7); `enrich/ascent_fwd|back f32[E]`,
   `enrich/forest u8[E]`, профили высот `prof_off/prof_ele`, `enrich/water_nodes u32[K,2]`;
   `pop/rides u16[E]`. **Дуга `a = 2·e + d`**: `reverse(a) = a^1`, `edge(a) = a>>1`; веса — `f32[2E]`.
3. **`kernel/`** (Rust) — CSR внутри; `Graph(edge_u, edge_v, node_lonlat)`,
   `route(src, dst, w) -> (arc_ids, cost) | None` (A*, эвристика — хорда на сфере),
   `sssp(src, w, aux, max_cost, reverse) -> (cost[N], metres[N], pred_arc[N])`.
   Контракт: `w[a]` = +inf или ≥ длины ребра (эвристика допустима). Про штрафы ядро не знает —
   Python правит свою копию весов. GIL отпускается, буферы thread-local с эпохами.
4. **`routing/`** — `spec.py`, `cost.py`, `via.py`, `generate.py`, `trim.py`, `score.py`,
   `diversity.py`, `gpx.py` (см. «Алгоритмы»).
5. **`tracks/` + `match/`** — `strava_zip.py`, `parse.py` (fitdecode, gpxpy, tcx), `clean.py`
   (выбросы, паузы, ресемплинг, разрыв по дыркам, обрезка по региону), `store.py`;
   `matcher.py` (Valhalla `trace_attributes`, costing `pedestrian` — игнорирует односторонки, как
   и велосипедисты; лимиты trace подняты) сохраняет результат **независимо от версии графа**:
   по треку список `(way_id, lon1, lat1, lon2, lat2)`; `project.py` — чистая функция, перекладывает
   сегменты на свои рёбра (концы → индексы узлов пути, ребро засчитывается при перекрытии ≥50%) и
   перезапускается при каждой пересборке графа; `popularity.py` → `rides[edge]`.
   Проеханность (≥2 заездов) снимает только мягкие ограничения, жёсткие исключения — никогда.
6. **`enrich/`** — `fetch.py`, `dem.py` (на ребро — набор в обе стороны для стоимости; набор
   маршрута считается по склеенному профилю со сглаживанием ~200 м и гистерезисом 5 м — GLO-30
   это модель поверхности и в лесу шумит), `landcover.py` (доля деревьев WorldCover в полосе
   ±25 м от ребра, а не по оси дороги), `water.py` (узлы выхода к воде по водоёмам от заданной
   площади и рекам, названия в SQLite).
7. **`nlu/`** — `client.py` (httpx, прокси), `prompt.py`, `resolve.py`. **Один вызов LLM** со
   структурированным выводом (JSON-схема; фолбэк — JSON в тексте + валидация pydantic и один
   повтор): топонимы возвращаются строками в именительном падеже, сервер сам ищет их в газеттире и
   сам формирует вопрос при неоднозначности или неизвестном старте. Уточнение = предыдущий
   RouteSpec + краткая статистика кандидатов + новая реплика → новый полный RouteSpec.
   «Не через Ревду» → `avoid` с радиусом по типу объекта; «вариант 2, но короче» →
   `anchor_candidate` (в v1 сохраняет сектор направления и категорию цели, не коридор).
8. **`api/`** — FastAPI, один воркер, `ThreadPoolExecutor` для маршрутов; SQLite (места, сессии,
   сохранённые маршруты). `POST /api/parse` (текст, точка клика, сессия → RouteSpec или вопрос),
   `POST /api/route` (RouteSpec → кандидаты), GPX, CRUD мест, загрузка треков. Valhalla в сервер
   не загружается: импорт — пакетный процесс, пишет новый файл популярности, сервер атомарно
   перечитывает.
9. **`web/`** — Vite + TypeScript + React + MapLibre GL JS, без роутера и стейт-библиотек:
   чат-панель, разобранный запрос чипами (видно, как сервис понял текст), карточки кандидатов,
   профиль высот, маркер старта кликом, управление местами, слой личной теплокарты, атрибуция
   источников (OSM, Copernicus, ESA WorldCover).
10. **CLI** (`typer`): `fetch-region`, `build-graph`, `enrich`, `import-tracks`, `match`,
    `pop-stats`, `route`, `eval`, `nlu-eval`, `serve`.

## Алгоритмы

**Стоимость дуги** (стартовые числа, настраиваются на странице `eval`):

`w = len · (1 + m̂·b_hw + f·(1−forest) + 1.5·φ·(1−pop) + hill) · S_mode[surface] · R · A · U`

- `m̂ = 0.3 + 1.7·avoid_major`; `b_hw`: cycleway/unclassified 0, track 0.05, residential 0.1,
  service/tertiary/path 0.15, pedestrian 0.2, footway 0.3, secondary 0.5, primary 1.2, trunk 3.0.
- `pop = min(1, ln(1+rides)/ln(31))`; по умолчанию φ = 0.4, f = 0.3, avoid_major = 0.5.
- `S_mode`: `any` почти нейтрален (bad ×1.8); `paved`: unknown ×2, likely_unpaved ×5,
  unpaved ×12, bad — запрет; `prefer_unpaved`: paved ×1.6.
- `R`: мягкое ограничение ×3 (×1 при ≥2 заездах), брод ×1.5. `A`: зона избегания ×8 (мягко).
- `U`: ребро уже использовано в этом маршруте ×20 (обе стороны), в уже принятом кандидате ×3,
  разворот на опорной точке — запрет. Итоговый множитель ограничен ×50.

**Один генератор** вместо четырёх: замкнутый или открытый обход через k опорных узлов, выбранных
из деревьев SSSP по предикату в полосе сетевого расстояния.
- Кольцо: k = 1–3, полоса ≈ L/(k+1), разброс по азимуту; узлы степени ≥3, не тупики.
- «К воде»: предикат — узел выхода к воде; маршрут, не дошедший до воды на 150 м, отбраковывается.
- A→B с длиной: прямой SSSP из A + обратный из B, опорные там, где dA + dB ≈ L.
- Подгонка длины итерациями, обрезка хвостов (`trim.py`), параллельно ~50 попыток.

**Невыполнимые длины:** A→B при L меньше кратчайшего d → кратчайший по предпочтениям с пометкой
«минимум N км»; при L < 1.15·d — только альтернативы методом штрафов; кольцо из тупикового
кармана — допускается «ножка» туда-обратно с указанием её доли.

**Оценка кандидата** (отдельно от стоимости дуг): штрафы за отклонение длины, долю повторов,
долю крупных дорог, недобор леса и знакомости, частоту поворотов. Жёсткие отказы: вне диапазона
длины; в режиме `paved` больше 10% грунта. Разнообразие: жадно по оценке, Жаккар по длине рёбер
< 0.4 без первых и последних 2 км (выезд из дома общий у всех колец). Пояснение к маршруту —
шаблоном из тех же признаков, без LLM.

## Ресурсы (оценки, уточняются на спайках)

| | |
|---|---|
| Сервер | 2 vCPU / 2 ГБ RAM, ~1 ГБ диска; граф в памяти 0.6–0.8 ГБ |
| Подготовка данных | 5–10 ГБ диска (pbf, тайлы Valhalla, DEM, WorldCover, архивы Strava), пик RAM 3–4 ГБ |
| Время сборки на 16 ядрах | граф 3–6 мин, тайлы Valhalla 3–8 мин, обогащение 5–10 мин, привязка 5000 треков 10–20 мин |
| Задержка запроса | LLM 1.5–4 с + движок 1–1.5 с локально (до ~4 с на 2 vCPU) |
| Деньги | LLM: доли цента за запрос, меньше $1 в месяц; данные и тайлы бесплатны |
| Доустановить локально | `uv`, `rustup`, `osmium-tool` |

## Этапы

Порядок — от самого рискованного; каждый этап заканчивается проверяемым артефактом.

**M0. Спайки (одноразовые скрипты в `spikes/`).**

| Спайк | Критерий | Запасной вариант |
|---|---|---|
| S1: тайлы Valhalla, `trace_attributes` на 20 реальных треках, проекция на свои рёбра | ≥95% сопоставленных км переложено, < 3 с на трек | геометрический матчер на своём графе (ближайшее ребро ≤15 м + проверка курса, покрытие ≥60%) → Valhalla в контейнере по HTTP |
| S2: Rust A* и SSSP на реальном графе | полный SSSP < 400 мс, отрезок 50 км < 30 мс | двунаправленный поиск / ALT, прореживание городских service/footway |
| S3: кольца 45/80/120 км от дома только по таблице классов дорог | ошибка длины ≤10%, повторы ≤5% | k=1 (точка разворота на L/2, два непересекающихся пути) как основной генератор |

**M1. Граф + ядро + A→B.** `osm/tags.py`, `osm/build.py`, `graph/store.py`, `graph/snap.py`,
`kernel/src/lib.rs`, `routing/cost.py`, `routing/path.py`, `viz/map.py`, `cli.py`, скелет
Containerfile. Тесты: ~60 случаев тегов; эталонная микрокарта `.opl` → ожидаемые массивы;
свойство «стоимость A* = Dijkstra scipy на случайных графах».
Проверка: `uv run rpa route --from 56.84,60.60 --to 56.80,59.93 --html out/ab.html`.

**M2. Генератор + оценка + eval.** `routing/spec.py`, `via.py`, `generate.py`, `trim.py`,
`score.py`, `diversity.py`, `eval/cases.yaml`, `eval/run.py`. Тесты-свойства: замкнутость, нет
разворотов после обрезки, нет запрещённых дуг; эталонные коридоры метрик на каждый кейс.
Проверка: `uv run rpa eval --out out/eval.html` (таблица метрик с порогами + карты).

**M3. Треки.** `tracks/*`, `match/*`. Тесты: по фикстуре на формат; синтетические треки —
обход графа с GPS-шумом — дают известную истину для матчера.
Проверка: `rpa match --jobs 12 && rpa pop-stats`, HTML-теплокарта; `familiarity` виден в `eval`.

**M4. Обогащение.** `enrich/*`. Тесты: синтетический растр-пандус даёт точный набор;
синтетическое озеро — ожидаемые узлы выхода.
Проверка: в `eval` появляются лес и набор, кейсы «к воде» проходят проверку 150 м.

**M5. API.** `api/app.py`, `db.py`, `routing/gpx.py`; контрактные тесты `TestClient`; curl к `/api/route`.

**M6. Текст.** `nlu/*`, `osm/gazetteer.py`; ~40 русских формулировок → ожидаемые поля RouteSpec
на записанных ответах LLM; `rpa nlu-eval --live` с реальным ключом через прокси.

**M7. Веб-интерфейс.** **M8. Контейнер** (3 стадии: rust+uv → node → `python:3.14-slim`;
`podman run --userns=keep-id -v ./data:/data:Z -p 8000:8000`), README, скрипт обновления данных.

Фикстуры: рукописная микрокарта `.opl` (односторонки, барьеры, зимник, разрезы), закоммиченная
реальная вырезка 1–3 МБ (город, озеро, лес), тесты `@pytest.mark.region` на полном графе —
только локально. Личные треки и `data/` — в `.gitignore`.

## Первые шаги после одобрения

1. `git init` (ветка `main`), `.gitignore`, каркас uv-workspace. Репозиторий позже уедет на GitHub,
   поэтому с первого коммита: `data/`, треки, `.env` и ключи — в `.gitignore`; конфиг — через
   `.env.example` без секретов; домашние координаты и личные места не хардкодятся (только в
   локальном конфиге/SQLite); README с указанием источников данных. Пуш на GitHub — отдельно,
   по явной команде.
2. Сохранить этот дизайн как `docs/superpowers/specs/2026-11-10-ride-path-advisor-design.md`, закоммитить.
3. Установить `uv`, `rustup`, `osmium-tool` (с подтверждением).
4. M0: спайки S2 и S3 можно начинать сразу; для S1 нужны реальные треки.
5. Скилл `superpowers:writing-plans` → детальный план M1; далее цикл план → реализация (TDD) по этапам.

**Нужно от пользователя:** запросить в Strava «Скачать свои данные» (архив приходит на почту
через несколько часов) для себя и друга и положить ZIP в `data/inbox/`; позже — ключ и адрес
LLM-провайдера и прокси (к этапу M6).

## Проверка

- `uv run pytest`, `cargo test` — юнит-тесты и свойства на фикстурах.
- `rpa eval` — HTML с эталонными запросами (включая три из постановки) на реальном графе,
  метрики с порогами и просмотр глазами после каждого этапа M2–M4.
- Сквозной прогон в веб-интерфейсе: три запроса из постановки → 2–3 разных маршрута, уточнение
  «короче» меняет результат, GPX открывается в стороннем просмотрщике.

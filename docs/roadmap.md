## Что построено

Команды: `fetch-region`, `build-graph`, `route`, `eval`, `import-tracks`, `match`, `pop-map`,
`enrich`, `serve`, `gazetteer`, `nlu-eval`, `sync-tracks`, `update`.

- **Граф** (`osm/`, `graph/`): рёбра — куски OSM-пути между узлами разреза, степень 2 не
  схлопывается; зимники, автомагистрали, стройки выброшены; только главная компонента.
  Покрытие — 6 классов уверенности с выводом `surface` → `tracktype` → класс дороги.
  Формат графа — версия 2 (каталог `<sha12>-v2`).
- **Пешие участки** (флаг ребра `DISMOUNT`, `osm/tags.py`): лестницы (`Highway.STEPS`),
  `highway=corridor|platform`, платформы `railway=platform` / `public_transport=platform` без
  тега `highway`, `bicycle=dismount`, закрытый доступ при разрешённом `foot`. Такое ребро не
  несёт `SOFT_RESTRICTED`. В регионе их 5086 (155 км), из них лестниц 4028. Маршрут сообщает
  `features.walk_m` и `walk_spans` — пары индексов координат на каждый непрерывный пеший
  отрезок; страница пишет «пешком N м» и рисует эти отрезки пунктиром.
- **Ядро** (`kernel/`): `Graph.route(src, dst, w)`, `Graph.sssp(src, w, aux, max_cost, reverse)`.
- **Веса** (`routing/cost.py`): `Prefs{avoid_major, surface, familiarity, forest, hills}`;
  `w = len · (1 + класс дороги + незнакомость + не-лес + подъём) · покрытие · ограничения`, потолок ×50.
  Пешее ребро — множитель ×8, после двух заездов по нему — ×3.
- **Генератор** (`routing/generate.py`): 36 попыток (1–3 опорные точки × 12 азимутов) в пуле
  потоков; обход со штрафом ×20 за повтор рёбер и запретом разворота на опорной точке; подгонка
  масштаба до попадания в длину; обрезка хвостов; оценка; жадный отбор с перекрытием < 0,4.
- **Петли-аппендиксы** (`routing/trim.py`): у опорной точки в стороне от естественной линии
  маршрут не может развернуться и оборачивается вокруг квартала — замкнутая петля с
  самопересечением. `tidy` вырезает такие петли короче 7 % целевой длины (не меньше 1 км) прямо
  при подгонке длины, не трогая петлю с обязательным узлом (вода); подгонка масштаба сама
  добирает километры. Оценка считает самопересечения (`Features.crossings`, −8 баллов за
  каждое, не больше трёх). На эталонах колец с мелкой петлёй было 8 из 24, стало 0.
- **Треки** (`tracks/`, `match/`): архив Strava читается по позициям колонок (заголовки
  локализованы); берутся только велозаезды (`RIDE_TYPES` в `tracks/ingest.py`), пропущенные типы
  печатаются. Привязка — Valhalla в процессе, результат хранится по OSM-путям
  (`data/match/matched.npz`) и не зависит от версии графа; `rides[e]` — число разных заездов по ребру.
  Тайлы Valhalla собираются из временной копии карты, где платформам без `highway` дописан
  `highway=footway` (`matcher.walkable_platforms`): иначе Valhalla по ним не ходит, и мост,
  к которому ведут только лестницы и платформы, для неё остров. С `highway=platform` она
  тоже не ходит — проверено на вырезке. Отметка `data/valhalla/source_sha256` хранит хеш карты
  и рецепт сборки, смена рецепта пересобирает тайлы.
- **Обогащение** (`enrich/`): узлы у воды (150 м) из OSM; лес из ESA WorldCover; высоты из
  Copernicus GLO-30 (пробы каждые ≤50 м вдоль рёбер). Растры читаются по сети, локально не кешируются.
- **Оценка** (`eval/`): 13 эталонных запросов, пороги: ≥2 кандидата, длина в допуске,
  повторы ≤5%, ≤5 с; места «через» пройдены по порядку (маршрут подходит к каждому ближе
  500 м, `VIA_REACH_M`); кольцо без длины приходит в трёх размерах, соседние различаются
  не меньше чем на 20 %. `p2p-peregon-bridge` (Палкинский Торфяник → Каменные палатки) требует
  пеший участок в первом варианте: 3,35 км со 108 м пешком через мост у станции Перегон
  против 15,3 км без него; после перепривязки мост хоженый, и через него идут все три варианта.
- **Отбор без заданной длины** (`routing/score.py`): из оценки вычитается до 60 баллов за
  превышение полной стоимости над самым дешёвым вариантом — иначе короткий маршрут с лестницей
  проигрывал объездам в десятки километров. Штраф за повороты ограничен 20 баллами.

- **Веб-API** (`api/`, `routing/gpx.py`): `create_app(engine, db_path)`; `rpa serve` слушает
  `127.0.0.1:8000`. `GET /api/meta`; `POST /api/route` (тело — `RouteSpec`; ответ: `request_id`,
  кандидаты с GeoJSON-геометрией, статистикой, профилем высот ≤ 500 точек, `warnings`, `message`
  при пустом результате); `GET /api/candidates/{id}.gpx`; CRUD `/api/places` (одно место по
  умолчанию, имена уникальны без учёта регистра). Точка дальше 2 км от дорог → 422, дальше
  500 м → предупреждение. SQLite `data/rpa.sqlite` (`api/db.py`): места и последние 200 запросов
  с кандидатами — `Db.request(id)` отдаёт прошлый `RouteSpec` и кандидатов для уточнений в M6.
  Описание схем — `/docs` у запущенного сервера.

- **`RouteSpec` для запросов словами** (`routing/spec.py`, `generate.py`): `via` — упорядоченный
  список точек, через которые надо проехать (до 8; подробности — ниже, «Несколько точек»);
  `avoid` — круги с множителем ×8; `bearing_deg` — кольца только в пределах ±45° от азимута.
- **Газеттир** (`osm/gazetteer.py`, `rpa gazetteer`): 21 тыс. мест из OSM (населённые пункты,
  станции, озёра, реки, вершины, парки) в `gazetteer.sqlite` в каталоге графа, сборка 7 с.
  Сравнение без родовых слов («озеро», «город»…), регистра, `ё` и окончаний; тёзки одного вида
  ближе 4 км склеиваются. Порядок: точные раньше неточных, названный вид («озеро …»), важность
  (город, посёлок, прочее, станция, река), расстояние.
- **Разбор текста** (`nlu/`): один вызов LLM → `ParsedRequest` (плоская структура, места —
  строками; промпт в `nlu/prompt.py`); `nlu/resolve.py` без LLM собирает `RouteSpec` или один
  вопрос. Старт: названное место → первая кликнутая точка → прежний старт (при уточнении) →
  место по умолчанию → вопрос. Тёзки: берётся единственный в старшем классе либо явно ближайший (вдвое и на 10 км
  ближе следующего), иначе вопрос с вариантами. Клиент (`nlu/client.py`): OpenAI-совместимый API,
  структурированный вывод с откатом на JSON в тексте, один повтор, `trust_env=False`, прокси из
  `LLM_PROXY_URL`. В модель уходят только текст, названия мест и статистика вариантов.
- **`POST /api/parse`**: `{text, points?, request_id?, picks?, understood?}` →
  `{spec | null, question | null, understood, warnings}`. `points` — кликнутые точки по порядку
  (до 9). `request_id` делает реплику уточнением прошлого запроса; `understood` (вернуть то, что
  пришло в прошлом ответе) пересобирает запрос без вызова модели — так отвечают на вопрос:
  кликом или выбором варианта (`picks: {question.about: option}`). Пустой `text` с точками
  или с `understood` собирается без модели (работает и при `has_llm = false`). Текст без
  LLM — 503, ошибка модели — 502, больше 8 промежуточных точек — 422.
  `/api/meta` сообщает `has_gazetteer` и `has_llm`.
- **Сохранённые маршруты**: `POST /api/routes {candidate_id, name?}`, `GET /api/routes`,
  `GET /api/routes/{id}` (с `spec` и `candidate`), `GET /api/routes/{id}.gpx`, `DELETE`. Маршрут
  копируется из кандидата и не зависит от очистки последних 200 запросов.
- **`GET /api/heatmap`**: проеханные дороги как GeoJSON, по одному `MultiLineString` на уровень
  (1, 2–4, 5–14, 15–49, 50+ заездов); 2,2 МБ, по сети 0,55 МБ (gzip); собирается при первом
  обращении. Та же функция (`viz/heat_page.py::ridden_roads`) рисует `rpa pop-map`.
- **Заезды без перезапуска**: `rpa match` заменяет `rides.npy` целиком; сервер перед
  `/api/route`, `/api/meta`, `/api/heatmap` сверяет время изменения и номер файла и, если он
  новый, подменяет счётчики (`api/app.py::_RidesFile`). Файл под другой граф игнорируется
  с записью в лог. Новый **граф** сервер не подхватывает — нужен перезапуск.
- **Загрузка треков** (`api/jobs.py::TrackImport`): `PUT /api/tracks/files/{name}` — тело запроса
  и есть файл, пишется потоком в `data/inbox` (временное имя с точкой, затем переименование;
  `.zip`, `.gpx`, `.fit`, `.tcx` и `.gz`; до 4 ГБ); `POST /api/tracks/import` запускает
  `python -m rpa sync-tracks` отдельным процессом, вывод — в `data/jobs/tracks.log`;
  `GET /api/tracks` — состояние, хвост журнала, файлы на сервере. Один запуск за раз, загрузка
  во время обработки — 409. Каждый запуск обрабатывает весь inbox заново.
- **`rpa sync-tracks`** = `import-tracks` + `match`. **`rpa update`** = `fetch-region` →
  `build-graph` → `gazetteer` → `enrich` (`--skip-fetch`, `--pbf`, `--no-rasters`).
- **Образ** (`Dockerfile`, 0,83 ГБ; имя понимают и podman, и Docker; `.dockerignore` тоже общий): сборка — `python:3.14-slim` + uv + rustup, страница —
  `node:24-slim`, итог — `python:3.14-slim` + `osmium-tool`, `.venv`, `web/dist`;
  `ENTRYPOINT rpa`, по умолчанию `serve --host 0.0.0.0`; данные в `/data`. Сервер в контейнере
  на реальном графе занимает 0,52 ГБ памяти.
- **Веб-интерфейс** (`web/`: Vite, React, TypeScript, MapLibre GL JS 6, тайлы OpenFreeMap).
  `npm run build` кладёт страницу в `web/dist`, её раздаёт `rpa serve` с корня (`RPA_WEB_DIR`
  меняет каталог). `index.html` отдаётся с `Cache-Control: no-cache`, файлы из `assets/` (имена
  с хешем содержимого) — с вечным кешем: без этого браузер часами показывал прежнюю страницу
  после пересборки. Слева панель: диалог, чипы «как понят запрос» (крестик снимает условие,
  «Изменить» открывает редактор длины, покрытия, рельефа и трёх ползунков), карточки вариантов
  (длина, набор, доли леса / знакомых / крупных дорог / грунта, GPX, «Сохранить»), профиль высот
  (наведение двигает точку по карте); выбор варианта — карточкой или кликом по линии —
  показывает его на карте целиком; точки маршрута ставятся кликами, двигаются и вставляются
  перетаскиванием линии (ниже, «Точки на карте»); вкладки «Места», «Сохранённые» и «Треки» (загрузка файлов,
  ход обработки, журнал); флажок «Мои заезды» — на карте.
  На узком экране карта сверху, панель снизу. Логика диалога — чистые функции с тестами:
  `web/src/session.ts` (тела запросов к `/api/parse`), `chips.ts`, `geo.ts`; `App.tsx` держит
  состояние, `components/` только рисуют. Протокол диалога описан в плане M7.

**Сделано в M10** (на реальном графе не запускалось):

- **Несколько точек** (`routing/generate.py`, `walk.py`): цепочка `старт → точки → финиш` (для
  кольца — обратно в старт) в названном порядке. `walk.route_legs` отдаёт плечи по отдельности;
  `_walk_via_places` сначала ведёт цепочку без разворотов, затем разрешает разворот в самих
  точках (место в тупике); хвосты и мелкие петли вырезаются (`trim.tidy`) по каждому отрезку
  между соседними точками, обязательные узлы не трогаются. `_passes_in_order` проверяет порядок
  после обрезки. Разнообразие — `_chain_alternatives`: рёбра найденной цепочки дорожают ×3, и
  она прокладывается заново; если после отбора (перекрытие ≤ 0,4) вариантов меньше, чем просили,
  добор идёт с перекрытием до 0,6 (`VIA_MAX_OVERLAP`). Длина вместе с точками: без длины —
  прямая цепочка, её альтернативы и объезды на ~20 % длиннее; длина меньше прямой — прямая с
  пометкой «через «A», «B» короче N км не получится»; длина больше — `_detours(lead=…)` удлиняет
  последнее плечо. Подпись варианта — названия точек через « → ». Точка, совпавшая со стартом
  или финишем, и повтор подряд выбрасываются.
- **Кольцо без длины** — три варианта разного размера (`Engine.loop_sizes_km`, по умолчанию
  30 / 50 / 80 км): `_loops` считает достижимость один раз и делает по 6 азимутов на размер со
  сдвигом 0° / 10° / 20° (54 попытки вместо 36); каждый размер подгоняется и оценивается в
  допуске ±15 % (уже, если размеры из истории ближе друг к другу: допуски соседних размеров не
  пересекаются), `diversity.select_by_size` берёт по одному варианту на размер, от короткого к
  длинному. То же для кольца «к воде» без длины. Вопрос «На сколько километров кольцо?» убран.
- **Размеры из истории заездов** (`match/sizes.py`): квартили 25 / 50 / 75 длины заездов (без
  `commute` и короче 10 км; нужно не меньше 20 заездов), округление до 5 км, соседние размеры
  различаются не меньше чем на 20 % — иначе размеры по умолчанию. `rpa match` пишет
  `ride_sizes.json` рядом с `rides.npy` (и удаляет устаревший), `build-graph` переносит его из
  прежнего каталога графа, сервер перечитывает без перезапуска (`_RidesFile`). Файл с нечисловыми, неположительными
  или неупорядоченными значениями игнорируется.
- **Привязка только к проезжаемым узлам** (`graph/snap.py`): `Engine.snapper` строится по узлам,
  у которых есть хотя бы одно ребро без `DISMOUNT`. Пешие узлы остаются в графе и доступны
  поиску пути, но старт, финиш и точка «через» на них больше не садятся.
- **Список мест в тексте** (`nlu/prompt.py`): `ParsedRequest.via: list[str]` — «из A в B через
  C и D» даёт `["C", "D"]`, «до X и обратно» — кольцо с `via = ["X"]`. `describe()` отдаёт
  модели и названный старт прошлого запроса (раньше старт не описывался): так при уточнении
  словами роли кликнутых точек не съезжают. Координаты в модель по-прежнему не уходят.
- **Роли кликнутых точек** (`nlu/resolve.py::assign_points`, чистая функция): первая точка —
  старт, если старт не назван словами; последняя — финиш, если финиш не назван и это не кольцо;
  одна точка без названий — только старт; остальные — промежуточные. Названные словами
  промежуточные места идут раньше кликнутых. Метки: «точка на карте» у кликнутых старта и
  финиша, «точка 1», «точка 2»… у промежуточных.
- **Кликнутые точки между репликами.** Список точек — вся правда о кликах: если запрос пришёл
  с `points`, метки кликов, которые модель вернула из описания прошлого запроса («точка на
  карте», «точка N»), отбрасываются (`without_clicked`), и в ответе `understood` уже без них.
  Если точек в запросе нет, такие метки берутся из прошлого запроса по роли: финиш — из
  прежнего финиша, «точка N» — из прежних промежуточных. Название, совпавшее с меткой первой
  или последней кликнутой точки («Старт отсюда» кладёт в список точку с именем места), тоже
  не считается названным стартом или финишем — иначе при уточнении «короче» такая точка
  превращалась бы в промежуточную.
- **Точки на карте** (`web/src/session.ts`, `App.tsx`, `MapView.tsx`): клик добавляет точку в
  конец списка (до 9); при двух точках маршрут строится сразу, без текста и без модели; дальше
  любая правка точек пересобирает запрос через `understood`. Маркеры: «С» — старт, «Ф» — финиш,
  номера — промежуточные; перетаскиваются; клик по промежуточной или финишу убирает точку, клик
  по старту при двух и более точках замыкает маршрут в кольцо и размыкает обратно. На каждую
  кликнутую промежуточную точку — чип «через: точка N ✕». Страница отправляет весь список с
  каждым запросом; роли для маркеров считает `pointRoles` — зеркало `assign_points`. Пока идёт
  запрос, точки не редактируются; неудачный запрос возвращает список к прежнему. Правки точек
  не множат в диалоге строки «Нашёл N вариантов» — служебная строка заменяется.
  Промежуточная точка дальше 2 км от дорог — 422, дальше 500 м — предупреждение, как у старта.
- **Перетаскивание линии** выбранного варианта ставит промежуточную точку: место в списке —
  по положению вдоль маршрута (`geo.ts::insertIndex`). Перед вставкой концы маршрута
  закрепляются (`session.ts::pinnedEnds`), чтобы новая точка не стала стартом у маршрута,
  начатого от места по умолчанию. Мышью — нажать и сдвинуть больше чем на 5 px; на сенсорном
  экране — после долгого нажатия (350 мс); второй палец отменяет захват, нажатие без движения
  точку не ставит.
- **База** (`api/db.py`): `PRAGMA user_version`, `SCHEMA_VERSION = 2`. База прежней версии при
  открытии теряет последние запросы и **сохранённые маршруты** (спеки старого формата);
  сохранённые места остаются. Так решено в дизайне; если сохранённые маршруты жалко, до первого
  запуска новой версии можно добавить перенос (`via`: `null` → `[]`, объект → список из него).

Замеры на реальном графе (808 тыс. узлов, 1,07 млн рёбер): запрос на 3 кольца — 0,6–0,8 с;
через HTTP — 0,7–0,8 с; сборка графа 12 с; привязка 1761 сегмента 40 с; обогащение 97 с.

## Данные

Всё в `data/` (не в git). Полная пересборка с нуля:

  без файла соответствующее предпочтение просто не действует.
- После M9 привязанных путей вне графа осталось 19 из 423; проеханных дорог — 2922 км
  (было 2914); заезды есть на 369 пеших рёбрах, на 197 — два и больше (скидка ×3). Мост,
  лестницы и платформы у станции Перегон — с заездами. Старый каталог графа `…-v1` больше не нужен, его можно удалить.
- Сейчас импортирован один архив (1743 заезда, 19,4 тыс. км в регионе). Архив второго
  пользователя — положить в `data/inbox/` и повторить `import-tracks` и `match`.

## Отличия кода от исходного дизайна

Дизайн (`specs/2026-11-10-…-design.md`) писался до реализации. Фактически:

- **Генератор колец** ставит опорные точки геометрически (углы правильного многоугольника с
  привязкой к «приятному» перекрёстку), а не по полосе сетевого расстояния из SSSP. SSSP-полоса
  используется только для A→B с целевой длиной.
- **`RouteSpec` сейчас**: `start`, `end`, `shape`, `length_km`, `prefs`, `via` (список точек),
  `via_category` (только `"water"`), `avoid`, `bearing_deg`, `n_candidates`. Кольцо без длины
  допустимо. Поля `anchor_candidate` нет:
  «вариант 2, но короче» превращается в `bearing_deg` (азимут на дальнюю точку того варианта)
  плюс новую длину.
- **Старт**: клик по карте важнее места по умолчанию (в дизайне было наоборот) — клик делается
  для конкретного запроса. Но названный словами старт важнее клика: тогда все кликнутые точки —
  промежуточные (и финиш).
- **Тесты разбора** идут не на записанных ответах модели, а на подставной модели и на готовых
  `ParsedRequest`; живую модель проверяет `rpa nlu-eval`.
- **Газеттир** без FTS-ранжирования: точное совпадение по таблице ключей, FTS5 — только для
  совпадений по началу слов. Улиц и именованных дорог в нём нет.
- **Привязка треков**: costing `bicycle` с `ignore_oneways` и `ignore_access`, а не `pedestrian`.
- **Лес**: WorldCover читается в 1/8 разрешения (80 м) со сглаживанием 3×3 вместо полосы ±25 м
  на полном разрешении.
- **Обогащение** лежит в каталоге графа плоско, без подкаталога `enrich/`; расстояния до воды нет,
  только узлы у воды.
- **Оценка кандидата** проще, чем в дизайне: длина, повторы, отношение стоимости к длине, повороты.
- **Не сделано из запланированного для M1–M4**: барьеры на узлах; зоны избегания в весах;
  закоммиченная реальная вырезка для тестов; вывод покрытия из скоростей треков.
- **Тесты ядра** — только из Python; `cargo test` не используется.
- **`bicycle=no` на пешеходной дорожке** остаётся мягким ограничением, а не пешим участком
  (в дизайне M9 было иначе): такая дорожка проезжаема, и два заезда снимают с неё штраф.
- **Точки маршрута и точка нового места — разные маркеры** (до M10 маркер был один на всё):
  на вкладке «Места» клик двигает только заготовку места. Список точек маршрута уходит в
  `/api/parse` с каждым запросом целиком (до M10 клик уходил, только если маркер двигали после
  последнего результата); названный словами старт при уточнении «короче» сохраняется за счёт
  того, что `describe()` теперь описывает его модели.
- **Метки кликнутых точек** нумеруются среди промежуточных («точка 1» — первая промежуточная),
  а не по всему списку, как в плане M10: так номер в чипе совпадает с номером на маркере.
- **Перетаскивание линии закрепляет концы маршрута** (`pinnedEnds`) — в плане M10 этого не было.
- **Правка чипов** пересобирает запрос в обстановке исходной реплики (те же `request_id`,
  `points`, `picks`), а не поверх показанного результата: так «как вариант 2» не меняет смысл.
- **Загрузка без multipart**: файл — тело `PUT`, поэтому не понадобилась зависимость
  `python-multipart`, а архив в сотни мегабайт не держится в памяти.
- **Обновление данных — команда `rpa update`**, а не скрипт: она же работает в контейнере.
- **`Dockerfile`, а не `Containerfile`**, и `.dockerignore`, а не `.containerignore`: эти имена
  находят и podman, и Docker. `compose.yaml` — только для Docker (`user: RPA_UID:RPA_GID`);
  rootless-podman нужен `--userns=keep-id`, которого в compose-файле для Docker быть не может.
- **Сохранённый маршрут нельзя переименовать**: имя — заголовок кандидата; своё имя принимает
  только API (`name`).
- **Фронтенд без компонентных тестов**: тестами покрыта логика, вёрстка и карта проверены
  прогоном в headless Chromium (Playwright ставился во временный каталог, в зависимости не внесён).

## Известные проблемы и что подстроить

- **Привязка рядом с платформами неоднозначна.** После того как Valhalla стала видеть
  платформы, в одном месте около 356 заездов переехали с пешеходной дорожки на идущие рядом
  платформу и велодорожку (примерно 0,5 км рёбер); всего счётчик изменился у 265 рёбер из
  1,07 млн. Какой вариант верен, по счётчикам не определить.
- **Платформы, размеченные только отношением-мультиполигоном**, в граф не попадают (как и
  площади `highway=pedestrian`); замкнутый контур платформы становится кольцом пеших рёбер.
- **В эталонных кольцах появились пешие метры**: 1240 м на 27 вариантов, самый длинный
  непрерывный отрезок 105 м, из них по хоженым рёбрам только 155 м. Если это мешает —
  поднять `DISMOUNT_FACTOR` в `routing/cost.py`.

- **Набор высоты, вероятно, завышен** в городе и лесу (модель поверхности видит крыши и кроны):
  374 м на 45 км по Екатеринбургу. Сверить с реальными заездами; при необходимости усилить
  сглаживание в `enrich/rasters.py::climb_m`.
- **Режим `paved` (шоссейный заезд)**: грунт стоит дороже повторного проезда асфальта —
  вероятный грунт ×25, явный ×40, неизвестное покрытие ×3 (повтор — ×20); вариант с грунтом
  больше 3 % отбраковывается. До правки (×5 и ×12, порог 10 %) в шоссейных кольцах было до
  8 % грунта, после — 0–2,4 %, асфальта 92–100 %. Покрытие в регионе размечено плохо (явный
  асфальт — 11 % длины дорог), поэтому дорога с неизвестным покрытием может оказаться грунтом.
  Доля леса в шоссейных маршрутах остаётся 45–70 %: асфальтовые дороги идут через лес, это
  не показатель покрытия. Тротуаров (`footway`) в них до 15 % — отдельный вопрос.
- **Маршруты «к воде»** могут дать два кольца к одному и тому же водоёму.
- **Маршрут через далёкое место** давал один вариант: все объезды делят дорогу туда, и отбор
  по разнообразию их отсеивал. В M10 добавлены альтернативы всей цепочки и добор с перекрытием
  до 0,6 — помогло ли, видно только на реальном графе. Точка в конце единственной дороги
  по-прежнему даст один вариант, это ожидаемо.
- **Названные словами промежуточные места всегда идут раньше кликнутых**: вставить клик между
  двумя названными местами нельзя. Поэтому у маршрута с местами «через», названными словами,
  линия не перетаскивается — страница пишет, что надо убрать чип «через: …» или поставить точку
  кликом (иначе новая точка проезжалась бы после названных и маршрут возвращался бы назад).
  Настоящее лечение — общий порядок названных и кликнутых точек в `ParsedRequest`.
- **Клик после запроса словами от места по умолчанию становится стартом**, а не промежуточной
  точкой: по правилу ролей первая кликнутая точка — старт, если старт не назван в тексте
  («кольцо 50 км», затем клик — старт переедет в клик). Чтобы клик стал промежуточной точкой,
  старт надо назвать («от дома …») либо потянуть линию маршрута.
- **Цепочка через несколько точек может оказаться медленной** на реальном графе: альтернативы
  цепочки считаются последовательно (до 6 проходов), а `_detours(lead=…)` на каждой попытке
  заново прокладывает и начальные плечи. Если `rpa eval` не уложится в 5 с — прокладывать
  начальные плечи один раз (`route_legs`), а на попытку пересчитывать только последнее.
- **Старт при двух и более точках кликом не убрать** (клик по нему замыкает кольцо) — только
  «Новый маршрут» или убрать остальные точки.
- **Зона избегания и чисто пешие рёбра**: `_with_avoided` ищет узлы через привязку, а она после
  M10 видит только проезжаемые узлы; ребро, оба конца которого пешие, внутри зоны не дорожает
  (оно и так стоит ×8).
- **Отсечение окончаний в газеттире грубое**: «Ключ» и «Ключи» различаются только приоритетом
  буквального совпадения. Улицы и тракты по названию не находятся.
- **«Кольцо через Ключи на 60 км»** берёт ближайшее из восьми сёл-тёзок (47 км от центра
  Екатеринбурга) без вопроса и отдаёт 95 км с пометкой: запрошенная длина при выборе места
  не учитывается, тёзки рангом ниже (деревни, урочища) не предлагаются.
- **Обработка треков всегда полная**: новый файл заново импортирует и привязывает весь inbox
  (сейчас около двух минут). Файлы из inbox не удаляются — это источник истины.
- **Прерванная обработка**: после перезапуска сервера состояние — «idle», журнал прошлого запуска
  не показывается; сам процесс `sync-tracks` при остановке сервера в контейнере погибает.
- **Привязка треков в контейнере на реальном архиве не запускалась** — проверена на микрокарте
  (загрузка со страницы → тайлы Valhalla → привязка → заезды учтены без перезапуска).
- **Под Docker ничего не запускалось** — его нет на машине разработки. Проверено podman: сборка
  из `Dockerfile`, действие `.dockerignore`, работа образа от произвольного пользователя (так его
  запускает `compose.yaml`). Сам `compose.yaml` не исполнялся.
- **`rpa update` в контейнере со скачиванием** не запускался (0,2 ГБ выгрузок и растры);
  проверен с `--skip-fetch --no-rasters` на микрокарте.
- **Нет автопроверки страницы в браузере**: после правок `web/` — пересобрать и пройти руками
  запрос, уточнение, вопрос с вариантами, сохранение, GPX, теплокарту.
- **Бандл 1,3 МБ** (0,37 МБ gzip), почти весь — MapLibre; для локального сервиса терпимо.
- **Замкнутые пути** (кольцевые развязки): заезд через замыкающий узел приписывается не той дуге.
- **Числа в весах и оценке** — стартовые, по `out/eval.html` всерьёз не подбирались.
- Карты `out/eval.html` и `out/heatmap.html` глазами проверял только пользователь (M1) — после
  M2–M4 их стоит пересмотреть.

## M10: что проверить на реальных данных

M10 написан в облачной сессии: там нет `data/`, сети к OSM и ключа модели. Проверено: тесты,
сборка страницы, API и страница на синтетической сетке дорог (headless Chromium: два клика дают
маршрут, третий делает прежний финиш промежуточной точкой, перетаскивание и удаление маркера,
замыкание кольца кликом по старту, перетаскивание линии мышью и эмуляцией касания — на A→B и
на кольце). Не проверено и остаётся сделать на машине с данными:

1. `uv sync` (ядро не менялось), `cd web && npm install && npm run build`.
2. `uv run rpa match` — появится `ride_sizes.json` в каталоге графа; посмотреть, какие три
   размера получились из истории.
3. `uv run rpa eval` — код возврата 0, каждый запрос ≤ 5 с. Три новых эталона:
   `p2p-revda-via-degtyarsk`, `loop-via-two`, `loop-no-length`. **Координаты Дегтярска, Верхней
   Пышмы и Берёзовского в `eval/cases.py` взяты из открытых справочников, а не из указателя
   названий** (его в облачной сессии не было) — сверить с `gazetteer.sqlite` и поправить, если
   точка легла мимо города. Отдельно замерить время кольца без длины (расчёт — ×1,3 к
   обычному кольцу) и маршрута через несколько точек (альтернативы цепочки считаются
   последовательно).
4. `uv run rpa nlu-eval` — промпт изменён (список `via`, «до X и обратно»), и модель теперь
   видит названный старт прошлого запроса; добавлены формулировки с двумя и тремя местами,
   кольцо без длины, «по лесу от дома».
5. `uv run rpa serve`, затем `curl --noproxy '*'` к `/api/parse` → `/api/route`: «из A в B
   через C и D», «кольцо через Ревду и Дегтярск», «кольцо по лесу от дома»; затем уточнение
   словами («короче») после маршрута, собранного кликами, — старт, финиш и промежуточные точки
   должны остаться на месте. Сервер должен стартовать на прежней `rpa.sqlite`: последние
   запросы и сохранённые маршруты очистятся, места останутся.
6. Страница руками, особенно на телефоне: захват линии долгим нажатием не должен мешать
   прокрутке карты.

Прочие кандидаты, по убыванию пользы:

1. Архив заездов второго пользователя: загрузить на вкладке «Треки».
2. Подбор чисел в весах и оценке по `out/eval.html` и по впечатлениям от реальных маршрутов;
   сверка набора высоты с реальными заездами.
3. Выбор тёзки с учётом запрошенной длины.
4. Инкрементальная обработка треков (привязывать только новые файлы).
5. Автопроверка страницы в браузере (Playwright) и компонентные тесты.
6. Переименование сохранённых маршрутов, удаление загруженных файлов со страницы.

## Окружение разработки

- Fedora, Python 3.14 (uv), Rust через rustup в `~/.cargo`, uv в `~/.local/bin`; `podman` есть,
  `docker` и системного `osmium-tool` нет — `fetch-region` собирает образ `rpa-osmium` сам.
- В окружении задан `HTTPS_PROXY`; httpx и rasterio берут его сами. Для cargo нужен
  `CARGO_HTTP_CAINFO` (см. `CLAUDE.md`).
- `/usr/bin/time` отсутствует — время мерить через `SECONDS` в bash.
- Node 24 LTS распакован в `~/.local/opt/node-v24.22.2-linux-x64`, ссылки `node`, `npm`, `npx` —
  в `~/.local/bin`. Зависимости фронтенда ставились с `npm install --before=2026-10-28`
  (ничего моложе двух недель). MapLibre 6 ищет свой worker рядом с собственным модулем —
  в `MapView.tsx` он подключён через `setWorkerUrl` и импорт `?url`, иначе после сборки карта пуста.
- podman есть на хосте, но не в песочнице редактора (Flatpak): оттуда он вызывается как
  `flatpak-spawn --host podman …`. Каталог `/tmp` у песочницы свой — тома монтировать из `$HOME`.
  На хосте SELinux в режиме enforcing: том нужен с `:Z` (или `--security-opt label=disable`,
  чтобы не перемечать каталог).
- Системного браузера нет. Страницу проверял headless Chromium из Playwright; ему нужно явно
  передать прокси из `HTTPS_PROXY` (логин и пароль отдельно) и исключение для `127.0.0.1`.
